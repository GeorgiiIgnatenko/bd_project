# Обязательная инфраструктура лабораторной 4

Это инструкция к исполняемому стенду.
[Подробный отчёт лабораторной 4](../docs/lab4-report.md) объясняет требования,
реализацию и теорию репликации с примерами и командами защиты.
Нужны Docker Compose v2, локальный образ `postgres:18` (при отсутствии Docker
скачает его), Python 3.10+ stdlib. Команды запускаются из корня репозитория.
Основной проект запускать не требуется.

## Как устроено

`scripts.recovery` задаёт отдельное имя проекта, два Compose-файла и случайный
локальный порт primary. Override `recovery/compose.yaml` расширяет корневой
`compose.yaml`; отдельного шаблона преподавателя, по уточнению пользователя, нет.

| Сервис | Назначение | Том |
| --- | --- | --- |
| postgres | primary; миграции 001–007, маленький demo seed, схема recovery_lab | pgdata |
| replica | физическая асинхронная replica, принимает WAL | replica_data |
| restore | отдельный чистый экземпляр для логического восстановления | restore_data |
| app | одноразовый SQL-клиент news_app по TCP к primary | нет |

Тома получают префикс имени проекта. `verify` создаёт уникальный проект
`bd-news-recovery-check-…`; ручные команды используют `bd-news-recovery`.
Основной `bd-news-labs` и его public/dev/load не изменяются. Не применяйте этот
override к основному проекту. Реплики и restore не публикуют сетевые порты.

Первый `up` вызывает обычный `start.sh` в окружении нового проекта: роли,
миграции, seed. Проверочные записи живут в `recovery_lab.probe`; клиент читает
реальные `public.news`, а изменения для эксперимента делает только в этой схеме.
Повторный `up` сохраняет данные и использует имеющуюся базовую копию replica.

Primary использует `wal_level=replica`, `max_wal_senders=5`, `wal_keep_size=64MB`.
`recovery/roles.sql` создаёт отдельного репликатора; HBA разрешает ему replication
через SCRAM из той же контейнерной сети и запрещает обычное подключение к БД.
`replica.sh` создаёт passfile 0600 и выполняет:

```sh
pg_basebackup -d 'host=postgres port=5432 user=news_replicator application_name=news_replica passfile=/var/lib/postgresql/replication.pgpass connect_timeout=5' \
  -D "$PGDATA" -R -X stream --checkpoint=fast -w
```

`-R` создаёт `standby.signal` и настройки подключения, `-X stream` сохраняет
необходимый WAL во время копирования. Пароля в аргументах и `primary_conninfo`
нет. При неоконченном копировании каталог не принимается за рабочую replica.
Слотов и архива WAL нет: длительный простой может потребовать новой базовой копии.

## Полная проверка

```sh
python3 -m scripts.recovery verify
```

Последовательно проверяются:

1. Новый primary и replica, `pg_is_in_recovery()` и состояние `streaming`.
2. Backup всей учебной БД в custom-формате, наличие закрытого файла.
3. Restore в новый экземпляр без пользовательских таблиц. Повреждённый архив
   отклоняется; SQL-ошибка 42P01 во время восстановления откатывает созданные объекты.
4. Полное совпадение таблиц, sequences и схемы после восстановления, фактические
   FK, валидность ограничений/индексов и журнал миграций. Схема включает владельцев,
   ACL, функции, триггеры и существующие политики. Повторный restore в непустой
   экземпляр отклоняется, чтобы не затереть данные.
5. Остановка replica: `news_app` продолжает читать и делать COMMIT в primary;
   после запуска replica получает пропущенный маркер.
6. Остановка primary: новый SQL-клиент получает сетевую ошибку `psql exit=2`.
   Он запускается с `--no-deps`, поэтому не поднимает primary незаметно.
   Replica остаётся standby. После явного запуска primary новое подключение
   работает, ранее подтверждённые данные совпадают, неуспешного маркера нет.
7. Совпадение таблиц primary/replica, повторный `up` без потери данных и очистка
   только временных контейнеров/томов этого запуска.

Ошибка проверки даёт ненулевой код, в том числе неожиданный успех негативного
сценария. Ожидание получения маркера ограничено 90 секундами. Это не замер lag.
При ошибке сохраняются диагностика и FAIL; строка полного PASS выводится только
после всех проверок и успешной очистки. Массовая генерация не выполняется.

## Пошаговые команды

```sh
python3 -m scripts.recovery up
python3 -m scripts.recovery backup
python3 -m scripts.recovery restore
python3 -m scripts.recovery outages
python3 -m scripts.recovery compose ps
```

`outages` можно повторять: у каждого эксперимента новые метки. `restore` разрешён
только в пустой экземпляр, а не поверх предыдущего восстановления. `backup`
заменяет предыдущий локальный дамп этого учебного проекта после успешного создания;
для отдельного набора используйте `--project bd-news-recovery-имя` **перед** командой.
В имени допустимы латинские строчные буквы, цифры и дефисы.

Сами backup и restore выполняют следующие команды внутри соответствующих сервисов
(точный код — `scripts/recovery.py`):

```sh
pg_dump -U news_bootstrap -d "$POSTGRES_DB" --format=custom
pg_restore -U news_bootstrap -d "$POSTGRES_DB" --single-transaction --exit-on-error /workspace/.secrets/recovery/bd-news-recovery/news.dump
```

Python направляет stdout `pg_dump` в временный файл 0600 и переименовывает его
только после успеха. `pg_restore` читает готовый файл. Пароли не передаются в
командной строке: обслуживание внутри контейнеров использует локальный peer.
Роли кластера создаёт существующий `security/roles.sql`; новые пароли берутся
из `.env`. На restore заранее создаётся только служебное расширение и роли,
предметные миграции не запускаются — все объекты восстанавливаются из dump.

Контрольный снимок снимается до/после backup; учебный стенд в это время должен
быть без сторонних записей. Дамп PostgreSQL согласован и при конкурентной записи,
но сравнение с внешним снимком в этом скрипте тогда намеренно отклоняется.
Dump охватывает одну БД, не файлы HBA, настройки сервера и глобальные роли:
их источники — Compose, `security/` и локальный `.env`.

Журнал хранится в `artifacts/recovery/<project>/events.txt`, снимок с числом строк
и отпечатками таблиц, sequences, схемы и дампа — в `backup.json` рядом.
В `restore.json` сохраняется полученный снимок восстановления. Сравнение схемы
нормализует случайный защитный токен pg_dump 18 и эквивалентную запись CHECK
с приведением массива литералов varchar к text: PostgreSQL после restore может
выводить приведение каждого элемента вместо всего массива. Значения и остальные
определения не исключаются из сравнения. Нормализованный SQL схемы для диагностики
сохраняется с 0600 рядом с дампом в `.secrets/recovery/<project>/`.
Тексты строк и пароли туда не выводятся. Дамп находится в
`.secrets/recovery/<project>/news.dump`, исключён из Git и закрыт правами 0600.
Это копия учебных аккаунтов; не прикладывайте её к открытому отчёту.

```sh
python3 -m scripts.recovery down
```

`down` явно удаляет все три тома **только этого учебного проекта**. Журнал и дамп
сохраняются. Последовательности на физической replica могут иметь другие
зарезервированные значения из WAL; после stop/start сравниваются строки таблиц,
а точное равенство sequences проверяется при логическом restore.

## Границы

Приложения пока нет; проверяется подключение и транзакция `news_app`, а не HTTP,
пул соединений или reconnect приложения. Используется штатная остановка Docker
с сохранением томов на одной машине. Потеря диска/узла и failover не имитируются.
Нет SSL, PITR, замеров replication lag/RTO/RPO, переноса аналитики на replica
или новых функций RLS/аудита. Асинхронная replica не гарантирует отсутствие потери
последних транзакций при настоящей катастрофе primary.

Восстановление при проблемах: [runbook](runbook.md).
Семантика инструментов: PostgreSQL 18 —
[pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html),
[pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html),
[streaming replication](https://www.postgresql.org/docs/18/warm-standby.html#STREAMING-REPLICATION).
