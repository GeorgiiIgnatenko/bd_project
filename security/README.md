# КТ-04 · Доступы и .env

Выполнены первые четыре обязательных пункта: три рабочие роли, запрет
суперпользовательских подключений приложения, демонстрация разрешённых и
запрещённых операций и исключение секретов из Git и открытой документации.

## Запуск

Нужны Docker с Compose v2 и Python 3. Из корня проекта:

```sh
sh start.sh
```

Скрипт проверяет `.env` в корне проекта. Если файла нет, создаёт его на основе
`.env.example` и заполняет пароли случайными значениями. Существующие непустые
значения сохраняются; недостающие параметры дополняются. Затем запускается
PostgreSQL и применяются роли и права. Этот же запуск обновляет старый том,
в котором первоначальным суперпользователем был `news_app`, без удаления данных.

В Git хранится только `.env.example`, где значения паролей пустые.
У каждого участника команды собственный локальный `.env` и собственная база Docker.
Абсолютных путей к папкам с секретами в конфигурации нет.

## Где находятся пароли

Все четыре пароля находятся **только в локальном `.env`**:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Служебная роль `news_bootstrap` |
| `ADMIN_PASSWORD` | Администратор `news_admin` |
| `APP_PASSWORD` | Приложение `news_app` |
| `ANALYST_PASSWORD` | Аналитик `news_analyst` |

Рядом задаются `POSTGRES_DB` и `POSTGRES_PORT`. Настоящие значения паролей
в инструкции не приводятся. `.env` имеет права `0600` и исключён из Git.
Для его создания отдельно от запуска базы: `python3 security/init_env.py`.

Compose передаёт каждому клиенту только его пароль. Вместо полного каталога
проекта клиентам монтируются SQL-файлы и каталоги с кодом: `.env` внутрь них
не попадает. PostgreSQL хранит пароли ролей в стандартном формате SCRAM-SHA-256;
отдельных файлов с verifier и `.pgpass` проект не создаёт.

Чтобы сменить пароль, измените соответствующую переменную в своём `.env`
и снова выполните `sh start.sh`. Скрипт не возвращает старые значения.
Не публикуйте `.env`, скриншоты паролей или вывод конфигурации контейнеров,
который может содержать переменные окружения.

Python-скрипты `experiments/` также читают настройки из `.env` и по умолчанию
подключаются как `news_admin`. При необходимости можно переопределить стандартные
переменные libpq: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGPASSFILE`.

## Роли и права

Это роли подключения PostgreSQL. Они отличаются от записей «Гость»,
«Зарегистрированный пользователь» и «Администратор» в таблице приложения `role`.

| Роль | Разрешено | Запрещено |
| --- | --- | --- |
| `news_admin` | Управление проектной БД, схемами, миграциями и данными | Стать суперпользователем, создавать роли кластера, читать серверные файлы и `pg_authid` |
| `news_app` | Чтение 12 таблиц `public`, запись по бизнес-сценариям | Изменение структуры, `TRUNCATE`, переписывание новостей и истории импорта, получение административных прав |
| `news_analyst` | Чтение публикаций и статистики | Запись данных, изменение структуры, чтение учётных записей, подписок и избранного |

Все три рабочие роли имеют `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`,
`NOREPLICATION`, `NOBYPASSRLS`, `NOINHERIT`. Лишнее членство в других ролях удаляется,
чтобы исключить повышение прав через `SET ROLE`.

| Таблицы | Права `news_app` |
| --- | --- |
| `role` | `SELECT` |
| `app_user`, `category`, `news_source`, `scrape_run` | `SELECT`, `INSERT`, `UPDATE` |
| `news`, `import_result`, `scrape_error_log` | `SELECT`, `INSERT` |
| `news_category`, `subscription_category`, `subscription_source`, `favorite` | `SELECT`, `INSERT`, `DELETE` |

Аналитику доступны восемь таблиц: `role`, `category`, `news_source`, `news`,
`news_category`, `scrape_run`, `import_result`, `scrape_error_log` в `public`
и существующих наборах `dev`, `load`, `lab3_dev`, `lab3_load`.
Права для новых таблиц выдаются явно в `grants.sql`.

Служебный суперпользователь `news_bootstrap` применяется только для установки
и локальной настройки внутри контейнера. Его сетевые подключения запрещены
в `pg_hba.conf`, даже с правильным паролем. Локальное обслуживание использует
`peer` и явные соответствия в `pg_ident.conf`.

При обновлении старого тома исходный суперпользователь переименовывается
в `news_bootstrap` с сохранением OID. Новая `news_app` получает ограниченные права,
проектные объекты передаются `news_admin`, системные каталоги остаются у bootstrap.
Временная локальная роль `news_setup` удаляется; старые сетевые сеансы завершаются.
Отдельно повторить настройку ролей можно командой `sh security/apply.sh`.

## Подключение и демонстрация

```sh
docker compose run --rm admin
docker compose run --rm app
docker compose run --rm analyst
sh security/demo.sh
```

Демонстрация использует три отдельных TCP-подключения с их настоящими паролями.
Администратор меняет пробную таблицу, приложение выполняет разрешённые операции
с данными, аналитик читает публикации и агрегаты. Запрещённые операции должны
дать `42501`; неожиданный успех прерывает сценарий. Отдельно проверяется запрет
сетевого входа под bootstrap. Успех — 32 сообщения `PASS` и код выхода 0.
Все пробные изменения откатываются без изменения реальных identity-счётчиков.

Сервисы `checks`, `seed_only` и генератор используют `news_admin`,
сервис `queries` — `news_app`. Прежние команды сохраняются:

```sh
docker compose run --rm checks
docker compose run --rm seed_only
docker compose run --rm queries
sh generator/run.sh dev 42
```

`seed_only` запускается один раз для пустых таблиц. Настройка прав конечных
пользователей внутри приложения остаётся его бизнес-логикой.

## Файлы

| Файл | Назначение |
| --- | --- |
| `../start.sh` | Подготовка `.env`, запуск PostgreSQL и применение прав |
| `init_env.py` | Создание `.env` из шаблона с сохранением существующих значений |
| `bootstrap.sql`, `roles.sql` | Учётные записи, безопасное обновление старого тома и владение объектами |
| `grants.sql` | Минимальные права рабочих ролей |
| `pg_hba.conf`, `pg_ident.conf` | Правила аутентификации |
| `apply.sh` | Применение настроек к запущенной базе |
| `demo_*.sql`, `demo.sh` | Разрешённые и запрещённые операции |
