# Лабораторная 4: роли, секреты, RLS и аудит

Здесь описаны первые четыре обязательных пункта и ранее выбранные RLS и аудит.
Оставшиеся обязательные backup/restore, replica, остановки и runbook описаны
в [recovery/README](../recovery/README.md). Новые дополнительные пункты не добавляются.

## Запуск и секреты

`sh start.sh` создаёт отсутствующий `.env`, сохраняет существующие пароли,
запускает PostgreSQL, применяет роли, права и недостающие миграции.
В Git хранится только `.env.example` с пустыми полями паролей.

| Переменная | Назначение |
| --- | --- |
| POSTGRES_PASSWORD | служебный news_bootstrap |
| ADMIN_PASSWORD | news_admin |
| APP_PASSWORD | news_app |
| ANALYST_PASSWORD | news_analyst |
| REPLICATION_PASSWORD | news_replicator, только изолированный стенд recovery |

У каждого участника свой локальный `.env` с правами 0600; пароли генерируются
через `secrets.token_urlsafe`. Сменить пароль: изменить `.env` и выполнить
`sh start.sh`. Не публиковать `.env`, вывод `docker compose config` и inspect
с переменными окружения. Роли используют SCRAM-SHA-256.

Клиентские контейнеры получают только свой пароль и выбранные SQL-каталоги;
`.env` им не монтируется. Сервер и владелец Docker считаются доверенными.
Python-стенды запускают psql внутри контейнера; секрет раскрывается только
как PGPASSWORD дочернего процесса, не как аргумент командной строки или отчёт.
Настройка паролей отключает запись utility-команд в pg_stat_statements и SQL-лог.

В стенде recovery репликатор имеет `REPLICATION`, но не `SUPERUSER`; HBA primary
разрешает ему только протокол репликации из внутренней сети. Его пароль хранится
в `.env` и passfile 0600 внутри replica; `primary_conninfo` содержит путь к passfile.
Дампы `.secrets/recovery/` закрыты правами 0600, исключены из Git и не входят
в публикуемые журналы. Роли и их пароли в логический dump не выгружаются:
на чистом restore роли создаются из SQL и локального `.env`.

## Права

Роли подключения PostgreSQL отличаются от предметного справочника `role`
(гость, зарегистрированный пользователь, администратор портала).

| Роль | Разрешено | Запрещено |
| --- | --- | --- |
| news_admin | владение проектной БД, схемы, миграции и данные | создание ролей кластера, SUPERUSER, серверные файлы и pg_authid |
| news_app | предметные чтение/запись в public | DDL, TRUNCATE, переписывание сохранённых новостей и истории, повышение прав |
| news_analyst | публикации, справочники, статистика импорта | запись, аккаунты, подписки, избранное, аудит |

Все три: NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS,
NOINHERIT. Настройка удаляет лишнее членство, исключая повышение через SET ROLE.
`news_admin` управляет только проектной БД, а не всем кластером.

| Таблицы public | Права приложения |
| --- | --- |
| role | SELECT |
| app_user, category, news_source, scrape_run | SELECT, INSERT, UPDATE |
| news, import_result, scrape_error_log | SELECT, INSERT |
| news_category, subscription_category, subscription_source, favorite | SELECT, INSERT, DELETE |

Аналитику доступны восемь неперсональных таблиц в public/dev/load. Q3 требует
все подписки и выполняется администратором; права аналитика ради него не расширяются.
Приложение не имеет доступа к dev/load, audit_log и schema_migration.

`news_bootstrap` — локальный служебный superuser. pg_hba.conf запрещает ему
TCP-вход даже с правильным паролем; локальный peer разрешён только root/postgres
внутри контейнера. Старый режим с суперпользователем news_app больше не поддерживается:
для одноразовых старых данных описан полный сброс в главном README.

## RLS

На favorite, subscription_category и subscription_source политика проверяет
`user_id = NULLIF(current_setting('app.current_user_id', true), '')::bigint`.
Приложение после аутентификации начинает транзакцию:

```sql
BEGIN;
SET LOCAL app.current_user_id = '1';
-- действия пользователя 1
COMMIT;
```

Без контекста/с пустым контекстом строк не видно и INSERT запрещён.
Чужой INSERT запрещён, DELETE чужих строк затрагивает 0 строк.
SET LOCAL сбрасывается при завершении транзакции, что важно при повторном
использовании подключения. Не устанавливать контекст обычным сессионным SET.

**Граница доверия:** news_app — роль серверного приложения. Обладатель прямого
SQL-доступа к ней может сам выставить любой ID. RLS здесь защищает запросы
от забытых фильтров, а не заменяет аутентификацию. Конечным пользователям пароль
этой роли не выдаётся. Администратор-владелец обходит RLS; аналитик не имеет GRANT
на персональные таблицы. Права редактирования аккаунтов — логика доверенного сервера.

## Аудит

Миграция 006 записывает INSERT/UPDATE/DELETE семи критичных таблиц: app_user,
news_source, news, news_category, favorite и обе подписки. Запись содержит время,
роль подключения/SET ROLE, app.current_user_id, таблицу, операцию и old/new JSONB.
Хеш пароля удаляется; смена отмечается флагом password_changed. UPDATE без
изменений не создаёт запись. Каскадные изменения журналируются.

Приложение и аналитик не читают и не меняют журнал. Обычные UPDATE/DELETE/TRUNCATE
журнала блокируются триггером, в том числе при выполнении владельцем.
Владелец таблицы или суперпользователь может отключить триггер: защита от
доверенного администратора не заявляется. Журнал транзакционный: откат отменяет
записи; неуспешные/отклонённые попытки сюда не входят. Пропуски identity допустимы.

```sh
sh scripts/view_audit.sh
```

## Демонстрация и автоматические проверки

```sh
sh security/demo.sh
bash tests/audit_rls_tests/run_rls_audit_tests.sh
python3 -m scripts.verify
```

`demo.sh` проверяет разрешения и SQLSTATE 42501 через три настоящих TCP-логина,
отдельно проверяет отказ bootstrap по pg_hba.conf. SQL-тест RLS/аудита использует
SET LOCAL ROLE внутри одной откатываемой транзакции: это проверки политик,
а не проверка паролей. Интеграционный runner дополнительно сравнивает персональную
ленту двух пользователей с результатом под реальным news_app.
Фикстуры откатываются; audit identity может увеличиться.
