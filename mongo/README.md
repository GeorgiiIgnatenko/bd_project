# MongoDB · лабораторная 5

Четыре коллекции, CRUD, embedding/reference и строгая валидация на небольшом
синтетическом наборе агрегатора. Нужны Docker Compose v2 и Python 3.10+ stdlib;
mongosh входит в официальный образ `mongo:8.0`.

## Запуск из корня репозитория

```sh
python3 -m scripts.mongo demo
python3 -m scripts.mongo verify
python3 -m scripts.mongo down
```

`demo` поднимает отдельный проект `bd-news-mongo`, **пересоздаёт только учебную
БД `lab5_demo`**, выполняет сценарии и оставляет данные для просмотра.
Повторный `demo` возвращает исходный демонстрационный набор. `up` только запускает
контейнер. `down` останавливает проект и сохраняет именованный том.

`verify` создаёт случайный проект `bd-news-mongo-check-<id>` и БД
`lab5_check_<id>`, выполняет те же CRUD-сценарии, отрицательные/граничные проверки
и проверки кодов выхода. Временные контейнер и том удаляются в `finally`.
Сохранённый demo и PostgreSQL не затрагиваются. Ошибка или неожиданный успех
негативного теста дают ненулевой код; журнал сохраняется и при отказе.

Контейнер имеет `network_mode: none`, mongod слушает loopback, порты на хосте
не публикуются. Доступ только через доверенный Docker exec. Аутентификация
приложения не моделируется, новые пароли не нужны; стенд не предназначен для
подключения внешних клиентов. Основной PostgreSQL Compose работает независимо.

## Посмотреть данные и валидаторы

После `demo`:

```sh
docker compose -f mongo/compose.yaml -p bd-news-mongo exec mongo \
  mongosh --quiet --norc lab5_demo
```

В mongosh:

```javascript
show collections
db.reading_lists.find()
db.articles.find({ _id: NumberLong("1000") })
db.article_events.find({ articleId: NumberLong("1000") })
db.getCollectionInfos({ name: "reading_lists" })[0].options
```

Прямой запуск того же демонстрационного файла в уже работающем контейнере:

```sh
docker compose -f mongo/compose.yaml -p bd-news-mongo exec -T \
  -e LAB_MONGO_DB=lab5_demo mongo mongosh --quiet --norc \
  --file /workspace/mongo/demo.js
```

Сценарии отказываются работать с именем БД вне `lab5_demo`/`lab5_check_<id>`.
Фикстуры не получены из настоящего PostgreSQL: ID пользователя, источника и
запуска — учебные ссылки. Внешние FK и автоматическая синхронизация двух БД
не реализованы. Все исходные новости и Q1–Q8 продолжают принадлежать PostgreSQL.

## Файлы и проверяемое поведение

| Файл | Назначение |
| --- | --- |
| [schema.js](schema.js) | Четыре коллекции, единственный источник валидаторов strict/error и индексов |
| [fixtures.js](fixtures.js) | Учебный снимок, BSON long/int/date, примеры 1:N и M:N |
| [crud.js](crud.js) | Исполняемые C/R/U/D каждой коллекции, вложенный update, ссылки и lookup |
| [verify.js](verify.js) | Типы, обязательность, границы, три бизнес-правила, неизменность при отказе, BSON-размер |
| [failure_probe.js](failure_probe.js) | Контролируемые ошибки для проверки ненулевого exit |
| [demo.js](demo.js), [scenario.js](scenario.js), [common.js](common.js) | Точки входа, общий сценарий и утверждения |
| [scripts/mongo.py](../scripts/mongo.py) | Запуск контейнеров, изоляция, очистка и журналы, без копий MongoDB-запросов |

Журналы: `artifacts/mongo/demo.txt`, `artifacts/mongo/verify-<id>.txt`.
Они содержат версии сервера/клиента, примеры документов, результат каждого
утверждения и реальный BSON-размер подборки. Это локальные воспроизводимые
артефакты, исключённые из Git. Команда `verify` печатает итоговый PASS только
после всех проверок и успешного удаления временного стенда.

Проверено 2026-11-04 на MongoDB 8.0.34 / mongosh 2.14.0: 170 утверждений
в verify и три проверки отказа процесса. Демонстрация проходит 20 утверждений.
Подборка с 200 элементами, заметками по 1000 кириллических символов и именем
100 символов заняла 411 551 байт BSON. Это размер указанного набора, не замер
производительности. Повторный verify, сохранность demo после down/up и очистка
при искусственной ошибке сценария также проверены.
