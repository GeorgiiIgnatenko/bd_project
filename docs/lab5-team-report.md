## 1. Какие вопросы решает SQL

| Запрос | Что узнаём и как считается результат |
|---|---|
| Q1. Лента | Чьи новости показать первыми? Две проверки `EXISTS` ищут подписку на источник или категорию. Сначала идут приоритетные новости, внутри группы — свежие. Остальные тоже попадают в ленту. |
| Q2. Поиск | Какие новости выбранной категории содержат этот текст? Соединяем новость, источник и категорию через таблицу связей. `ILIKE` ищет подстроку в заголовке или содержании без учёта регистра. |
| Q3. Категории | Сколько у категории новостей за период и подписчиков сейчас? Считаем два набора отдельно в CTE, затем соединяем результаты. Иначе две новости и три подписчика дали бы шесть строк и завышенные счётчики. |
| Q4. Импорт | Сколько было запусков и чем закончились материалы? `COUNT(DISTINCT)` считает каждый запуск один раз, агрегаты с `FILTER` разделяют успехи, дубликаты и ошибки материалов. `LEFT JOIN` сохраняет источники без запусков. |
| Q5. Проблемные источники | У кого за период было хотя бы N неудачных запусков? Сначала группируем сообщения по запуску, затем считаем запуски по источнику и отбираем группы через `HAVING`. Даже запуск без сообщения считается. |
| Q6. Рейтинг | Кто больше пишет в каждой категории? Группируем публикации по категории и источнику. `DENSE_RANK()` раздаёт места внутри категории: результатам 3, 3, 1 соответствуют места 1, 1, 2. |
| Q7. Паузы | Сколько прошло между соседними публикациями источника? `LAG` находит предыдущее время в выбранном периоде. Первая строка даёт NULL, две одновременные публикации — ноль. Пагинация применяется после вычисления паузы. |
| Q8. Динамика | Сколько источник публиковал каждый день? Заполняем календарь полных суток UTC, дни без новостей получают ноль. Оконная сумма накапливает итог, среднее берёт текущий день и шесть предыдущих. В начале периода используются доступные дни. |

**Как объяснить окно.** В Q6 обычный `COUNT` сворачивает новости в одну строку для каждого источника внутри категории. Оконная функция добавляет к этой строке место среди соседей. Обе операции нужны в одном запросе.

| Критерий каталога | Покрытие |
|---|---|
| Агрегаты, минимум 3 | Q3, Q4, Q5, Q6, Q8 |
| Оконные функции, минимум 3 | Q6, Q7, Q8. Вместе показаны ранжирование, LAG, накопительный и скользящий агрегаты |
| CTE или подзапросы, минимум 2 | Q1, Q3, Q5, Q6, Q7, Q8 |
| Соединения нескольких таблиц, минимум 5 | Q1–Q7 напрямую соединяют предметные таблицы. Q8 также соединяет источник с календарём и дневным подсчётом |

## 2. Кто владеет данными и почему коллекции выглядят именно так

PostgreSQL хранит исходные новости и справочники, пользователей, подписки, избранное, запуски сбора, результаты, ошибки и аудит. Здесь важны внешние ключи и согласованная запись нескольких таблиц при импорте. Если заголовки разошлись, верным считается заголовок PostgreSQL. Учебный стенд MongoDB получает синтетические карточки из [fixtures.js](../mongo/fixtures.js). Автоматическую доставку между БД предстоит реализовать отдельно.

| Задача | Владелец факта | Как чтение, изменения и рост повлияли на модель |
|---|---|---|
| Открыть карточку | PostgreSQL, в MongoDB хранится проекция `articles` | Вкладываем имя источника и категории. Одно чтение отдаёт готовую карточку. При переименовании категории копии потребуется обновить. |
| Записать просмотр | MongoDB, `article_events` | Одно событие — отдельный документ со ссылкой на статью. Просмотров может быть сколько угодно. Новое событие добавляется без увеличения карточки. |
| Разобрать исходный ответ | MongoDB, `import_payloads` | У поставщиков разные поля. В `raw` сохраняются вложенный объект API или строка RSS. Идентификатор запуска связывает ответ с историей импорта в PostgreSQL. |
| Открыть подборку | MongoDB, `reading_lists` | Дату и заметку встраиваем в элемент списка. Текст общей статьи получаем по ссылке, поэтому исправление текста не требует менять каждую подборку. Встроенный массив ограничен 200 элементами. |

**Как показать обе связи.** В демо у статьи 1000 два события, просмотр и переход (1:N). Подборка A содержит статьи 1000 и 1001, подборка B тоже содержит 1000 (M:N). В `items` лежат ссылки. Операция `$lookup` по этим ID возвращает карточки. Наличие ID в документе само по себе не гарантирует существование другой записи.

## 3. CRUD и три бизнес-правила

CRUD — создать, прочитать, изменить, удалить. Команда `demo` через Python запускает клиент `mongosh`, который отправляет команды реальному серверу. Сервер применяет валидатор при записи. Сценарий проверяет результат чтением и количеством изменённых документов. [Исполняемый CRUD](../mongo/crud.js) · [Валидаторы](../mongo/schema.js)

| Временный документ | Какие действия показывает сценарий |
|---|---|
| Статья | Создать карточку и прочитать заголовок, применить исправление заголовка, отметить удаление через `deletedAt`, удалить учебную копию. |
| Событие | Записать просмотр и прочитать его, обезличить через `userId: null`, удалить и проверить отсутствие. |
| Ответ источника | Записать и прочитать RSS, исправить сохранённый текст, удалить документ. |
| Подборка | Создать список с одной статьёй и прочитать, добавить вторую, изменить её заметку на «Прочитано». Удаление с чужим ID владельца затрагивает ноль документов, с верным — один. Фильтр предполагает доверенный ID пользователя. |

**Бизнес-правила:** (1) в подборке максимум 200 элементов, (2) одна статья встречается в ней один раз, даже если отличаются заметки, (3) у ответа `json_api` поле `raw` содержит объект, у `rss` — непустую строку. Для второго правила сервер извлекает ID и сравнивает длину массива с числом различных ID. Дополнительно все четыре коллекции проверяют типы и обязательные поля в режиме `strict/error`. Пример: строка `"1000"` вместо BSON long отклоняется с кодом 121. Конфликт уникального URL даёт отдельный код 11000.

При несовпадении `check_that` бросает исключение, команда завершается с ошибкой. Контрольные данные живут внутри транзакции с откатом. [Тесты с ожидаемыми значениями](../tests/queries.sql) · [Запуск](../scripts/verify.py)

| Что можно случайно сломать | Как это заметит тест |
|---|---|
| Q1/Q2: приоритет ленты или поиск только в заголовке | В однодневном окне Q1 самая новая неподписанная статья оказывается на третьей позиции. В Q2 ожидаются ровно два ID: одно совпадение в заголовке, другое в содержании. Совпадение в чужой категории исключается. |
| Q3/Q4/Q5: удвоение строк при соединении | Q3 ожидает 2 новости и 2 подписчиков. Q4 сохраняет 2 запуска без материалов. Q5 считает 2 неудачных запуска, хотя оба сообщения относятся только к одному из них. |
| Q6/Q7/Q8: ошибка окна или границы | Q6 сохраняет обоих лидеров на первом месте. Q7 проверяет, в частности, паузы 25 часов и 0. В Q8 после ряда 1, 2, 0, 0, 0, 0, 0, 0 итог равен 3, а среднее на восьмой день равно 0,29: первый день уже вышел из окна. |

## 5. Желательное. Словарь коллекций и полей

Словарь описывает действующую схему v1. Все перечисленные поля обязательны, кроме помеченных «по желанию». Обязательное поле с допустимым `null` должно присутствовать. Идентификаторы типа `long` и `int` положительные. Даты хранятся как BSON date. У собственных документов MongoDB тип ключа — ObjectId. [Схема и индексы](../mongo/schema.js)

| Коллекция | Поле | BSON-тип и назначение |
|---|---|---|
| articles | _id | long, ID исходной новости PostgreSQL |

| | title, content | string, заголовок и текст, каждый содержит непробельный символ |
| | publishedAt | date, момент публикации |
| | source | object, снимок источника |
| | source.id, source.name | int и string, ID и непустое имя до 255 символов |
| | categories | array, минимум один снимок категории |
| | categories[].id, categories[].name | int и string, ID и непустое имя до 255 символов |
| | deletedAt | date или null, момент обнаружения удаления либо действующая карточка |
| article_events | _id | objectId, ключ события |
| | articleId | long, ссылка на статью |
| | userId | long или null, пользователь либо анонимное событие |

## 6. Желательное. Как изменить версию документа

Пример будущего требования: пользователь хочет архивировать подборку. Сейчас версия v1 подразумевается: поля версии нет, а сервер запрещает неизвестные поля. Для v2 предлагаем обязательные поля `schemaVersion: NumberInt(2)` и `archived: true/false`. У прежней подборки значение по умолчанию — `false`. Это стратегия перехода для следующего изменения. Действующий стенд использует v1.

| Этап | Действие и проверка |
|---|---|
| Подготовить чтение | Выпустить читатель обеих форм. Если версии нет, читать как v1 и показывать обычную подборку. Если версия равна 2, учитывать `archived`. Неизвестную версию регистрировать как ошибку. |
| Разрешить переход | Через `collMod` задать валидатор с двумя допустимыми формами. У v1 оба новых поля отсутствуют, у v2 оба обязательны и типизированы. Для обеих форм сохраняются лимит и уникальность статей. Проверить на копии, что обе формы принимаются, а половинчатый документ и дубли отклоняются. |
| Переключить запись | Когда все читатели готовы, переключить всех писателей на v2. Новые подборки получают версию 2. При обновлении старой подборки присвоить оба поля одной операцией. |
| Довести старые данные | Пакетами обновлять документы с отсутствующей версией, одним `$set` добавляя версию и `archived: false`. Повторный запуск пропустит v2 и сохранит уже выставленное `archived: true`. Сравнить количество документов, ID и содержимое `items` до и после. |
| Завершить или остановить | После нулевого количества v1 и проверки всех писателей оставить только форму v2. При сбое остановить обработку, сохранить двойной валидатор и совместимый читатель, затем продолжить по тому же фильтру. Для возврата приложения использовать сборку, умеющую читать обе формы. |

## 7. Восхитительное. До какого размера безопасно встраивать подборку

**Вопрос.** Если все читатели заполнят заметки до предела, поместится ли подборка из 200 статей в один документ? Измеряем на сервере размер целого BSON-документа, включая имена полей, ключи массива, даты и идентификаторы. [Сценарий измерения](../mongo/growth.js)

**Метод.** Команда `python3 -m scripts.mongo growth` запускает отдельную временную MongoDB с действующим валидатором. Для каждого профиля создаётся подборка с именем из 100 четырёхбайтовых символов. В неё порциями добавляются элементы с разными ID, фиксированной датой и заметкой. На каждом шаге сервер возвращает число элементов через `$size` и размер документа через `$bsonSize`. После 200 пробуем добавить ещё один элемент. Скрипт проверяет код ошибки и совпадение всего документа до и после отказа, затем обёртка удаляет временный стенд.

**Результат на MongoDB 8.0.34.** Все значения в таблице — байты BSON. В первом профиле заметка «Прочитать», во втором — 1000 букв «я», в третьем — 1000 символов 😀. Число символов во втором и третьем профиле одинаковое, но одна буква «я» занимает в UTF-8 два байта, а выбранный эмодзи — четыре.

| Элементов | Короткая заметка | Длинная, кириллица | Длинная, 4 байта на символ |
|---:|---:|---:|---:|
| 0 | 461 | 461 | 461 |
| 1 | 534 | 2 516 | 4 516 |
| 10 | 1 191 | 21 011 | 41 011 |
| 50 | 4 151 | 103 251 | 203 251 |
| 100 | 7 851 | 206 051 | 406 051 |
| 150 | 11 601 | 308 901 | 608 901 |
| 200 | 15 351 | 411 751 | 811 751 |
| 201 | отказ 121 | отказ 121 | отказ 121 |

**Вывод для портала.** Оставляем до **200 статей на документ**, с именем до 100 и заметкой до 1000 символов. Даже при заполнении всех полей и четырёх байтах на каждый символ подборка занимает **811 751 байт**, около **4,84%** от сообщённого сервером предела 16 777 216 байт. Остальные поля имеют фиксированные типы, а схема запрещает произвольные добавочные поля. Поэтому у текущего формата есть запас по размеру даже на самой длинной допустимой записи. Элемент 201 отклоняет наш `maxItems`. При добавлении новых полей или изменении лимитов эксперимент следует повторить. Здесь измерялся размер документа, скорость записи отдельно не оценивалась.

## 8. Как запустить и что показать

Команды выполняются из корня репозитория с Docker Compose и Python 3. Проверки PostgreSQL и MongoDB создают свои тестовые базы. Для автопроверок SQL генерировать большую схему `dev` не требуется.

```sh
sh start.sh
python3 -m scripts.verify
docker compose run --rm -T queries
python3 -m scripts.mongo demo
python3 -m scripts.mongo verify
python3 -m scripts.mongo growth
```

1. **SQL.** У `scripts.verify` ожидайте строку `PASS: migrations, constraints, lifecycles, roles, RLS/audit, transactions and queries`. Результаты отдельных проверок записаны в `artifacts/verification/core.txt`. Команда `queries` показывает сам каталог и заканчивается `COMMIT`. На новой пустой базе для видимых примеров один раз выполните `docker compose run --rm -T seed_only` перед `queries`. Исторические примеры dev/42 и фиксированная дата описаны в [подробном отчёте, раздел 6](lab5-report.md#sql-demo).
2. **Документы.** Команда `demo` пересоздаёт только учебную `lab5_demo`. После демонстрации остаются две карточки, два события, один исходный ответ и две подборки. Для показа откройте клиент командой ниже и выполните `db.reading_lists.findOne()`. Найдите `items[0].note` и `items[0].articleId`: заметка хранится внутри списка, ID ведёт к общей карточке.
3. **Правила.** `verify` проверяет CRUD, связи и отказы, печатает 170 успешных утверждений и три ожидаемых отказа отдельных процессов. Итог обёртки — `PASS: MongoDB verify`.
4. **Эксперимент.** `growth` выводит 21 замер и результаты попыток добавить 201-й элемент. Сопоставьте две последние колонки при 200 элементах и объясните разницу в кодировке. Журнал лежит по пути `artifacts/mongo/growth-<id>.txt`, который команда выводит в конце.

```sh
docker compose -f mongo/compose.yaml -p bd-news-mongo exec mongo mongosh --quiet --norc lab5_demo
```
