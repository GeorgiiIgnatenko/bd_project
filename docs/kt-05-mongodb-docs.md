# Документная модель MongoDB

Документ проектирует разделение данных PostgreSQL/MongoDB, задачи документной
модели и четыре коллекции со связями 1:N и M:N.

**Статус: проектирование.** Работающий стенд использует только PostgreSQL.
Сервис MongoDB, создание коллекций, их валидаторы, индексы, проверка доступа и
синхронизация ещё не реализованы. Все правила ниже — требования к будущей
реализации, а JSON — примеры структуры, не результаты запуска MongoDB.

## 1. Принцип разделения

PostgreSQL остаётся основной базой для данных со строгими связями, транзакциями
и требованиями к целостности. MongoDB выбрана для изменчивых документов,
проекции карточки новости и ограниченных вложенных подборок. Исходные новости
и их категории из PostgreSQL не переносятся и не удаляются.

## 2. Задачи для MongoDB

| № | Задача | Реляционный вариант | Причина выбора документной модели |
|---|---|---|---|
| T1 | Отображение карточки новости | Для нормализованных новости, источника и категорий нужен JOIN или отдельная проекция. | Карточка читается целым документом со снимками источника и категорий; допустимо отставание копии. |
| T2 | Хранение ответов источников | Возможны отдельные типизированные поля или JSONB для разных форматов. | Исходный payload сохраняется вложенным документом без унификации всех полей разных поставщиков. |
| T3 | Хранение событий по новостям | Возможна отдельная таблица событий, в том числе с JSONB. | События разных типов могут иметь разные дополнительные поля; каждый факт хранится отдельным документом, не раздувая карточку новости. |
| T4 | Пользовательские подборки | Подборка и элементы хранятся в связанных таблицах. | Ограниченная подборка читается целиком; её элементы можно изменять атомарно внутри одного документа. |

Это выбор структуры и границ данных, а не доказательство ускорения.
PostgreSQL также умеет хранить JSONB; перенос событий сам по себе не решает
задачи производительности или RLS. Вложение связанных данных позволяет
читать и изменять их в одном документе; неограниченно растущие события
остаются отдельной коллекцией. [Документация MongoDB](https://www.mongodb.com/docs/manual/data-modeling/embedding/).

В PostgreSQL остаются: новости и их категории (`news`, `news_category`),
учётные записи и роли, справочники (`category`, `news_source`),
подписки и избранное, запуски сбора и результаты импорта,
аналитические запросы Q1-Q8, журнал аудита, журнал миграций.

## 3. Модель владения данными

| Данные | Где хранятся | Источник истины |
|---|---|---|
| Пользователи, роли | PostgreSQL | PostgreSQL |
| Категории, источники | PostgreSQL | PostgreSQL |
| Новости и их категории | PostgreSQL | PostgreSQL |
| Подписки, избранное | PostgreSQL | PostgreSQL |
| Запуски сбора, результаты импорта, ошибки | PostgreSQL | PostgreSQL |
| Журнал аудита, журнал миграций | PostgreSQL | PostgreSQL |
| Копия новости для быстрого чтения (`articles`) | MongoDB | PostgreSQL |
| Сырые ответы источников (`import_payloads`) | MongoDB | MongoDB |
| События по новостям (`article_events`) | MongoDB | MongoDB |
| Подборки пользователей (`reading_lists`) | MongoDB | MongoDB |

### Правила согласованности

1. Каждый факт изменяется только в своей основной базе. `articles` обновляет
   отдельный процесс построения копии: независимое редактирование одной новости
   в двух базах запрещено. Пароли, хеши, подписки и избранное в проекцию не входят.
2. `articles` — копия новостей из PostgreSQL. Вручную её не правим, а при расхождении верим PostgreSQL.
3. Транзакция импорта остаётся в PostgreSQL.
   Публикация в MongoDB предполагается после `COMMIT`, с возможным отставанием.
   Общей транзакции между базами нет: сбой копирования не откатывает импорт.
   Повторная сборка карточки по `news.id` заменяет документ с тем же `_id`,
   не создавая дубликат. После сбоя нужна сверка или полная пересборка проекции
   из согласованного снимка PostgreSQL; одного вызова после COMMIT недостаточно
   для гарантированной доставки. Переименование источника и изменение категорий
   также должны обновлять вложенные снимки.
4. При удалении новости в PostgreSQL существующая копия в `articles` получает
   `deletedAt` — время обнаружения удаления при сверке, а не точное время SQL DELETE.
   Отсутствие исходной новости выявляется по снимку PostgreSQL. Сборки
   проекции выполняются последовательно, чтобы устаревший снимок не восстановил
   удалённую новость. Приложение скрывает такую карточку и её элементы в подборках;
   прежние события сохраняются как история. Ссылка не становится внешним ключом.
5. Подписки и избранное остаются в PostgreSQL, поскольку используют RLS. Подборки
   MongoDB — отдельная функция с именем и заметками, они не заменяют `favorite`.
   Доступ по `reading_lists.userId` проверяет доверенное приложение: PostgreSQL RLS
   на MongoDB не распространяется. Ссылки на пользователя и запуск сбора также
   проверяет приложение; создание списка для отсутствующего пользователя запрещено.

Процессы обновления, сверки и проверки ссылок здесь описаны, но пока не написаны.

## 4. Коллекции

Четыре коллекции. Идентификаторы и даты в примерах показаны обычным JSON для
читаемости. При записи `articles._id`, `articleId`, `userId` и `scrapeRunId`
должны иметь тип BSON `long` (соответствует SQL BIGINT), `sourceId`, `source.id`
и `categories[].id` — `int` (SQL INTEGER). Времена — BSON `date`, `deletedAt` —
`date` или `null`. В остальных трёх коллекциях `_id` типа ObjectId создаётся
при вставке. Строковые даты из примеров требуют преобразования; для обмена
с сохранением типов используется [Extended JSON](https://www.mongodb.com/docs/manual/reference/mongodb-extended-json/).

### 4.1. `articles` - карточка новости (T1), связь 1:1

Источник истины: PostgreSQL.

```json
{
  "_id": 1000,
  "canonicalUrl": "https://sportexpress.example/news/transfer-window",
  "title": "Итоги зимнего трансферного окна",
  "content": "Клубы завершили сделки…",
  "publishedAt": "2026-10-01T10:00:00Z",
  "source": { "id": 2, "name": "Sport Express API" },
  "categories": [ { "id": 2, "name": "Спорт" } ],
  "deletedAt": null
}
```
`_id` совпадает с `news.id` в PostgreSQL. `canonicalUrl`, `title`, `content`,
`publishedAt` берутся из `news`; `source` — из `news_source`, `categories` —
из `news_category JOIN category`. Источник и категории — копии справочников,
а не новые независимые сущности. Дополнительные поля поставщика, например автор,
предусмотрены только в `import_payloads.raw`: в SQL-модели поля автора нет.

### 4.2. `article_events`  - события новости (T3), связь 1:N

Поток событий. Одна новость, много событий. Каждое событие ссылается на новость через `articleId`.
Источник истины — MongoDB. Поля `articleId`, `type`, `at` обязательны;
`userId` — идентификатор авторизованного пользователя либо `null` для гостя.
`type` задаётся приложением (`view`, `click`); расширяемые сведения события
могут храниться в объекте `details`. Пользователь не задаёт чужой `userId`.

```json
{
  "articleId": 1000,
  "userId": 1,
  "type": "view",
  "at": "2026-10-02T08:15:00Z"
}
```

### 4.3. `import_payloads` - сырые ответы источников (T2), связь 1:N

Один запуск сбора, много сырых элементов. Ссылка на запуск: `scrapeRunId`.
Источник истины самого ответа — MongoDB, запуска и источника — PostgreSQL.
Все показанные поля обязательны. `sourceId` должен совпадать с источником
указанного `scrape_run`. Для `format=json_api` поле `raw` — объект, для
`format=rss` — исходная XML-строка; формат определяет ожидаемую форму payload.

```json
{
  "scrapeRunId": 7,
  "sourceId": 2,
  "format": "json_api",
  "receivedAt": "2026-10-01T10:00:02Z",
  "raw": { "…": "ответ источника" }
}
```

### 4.4. `reading_lists` - подборки пользователя (T4), связь M:N

Пользователь составляет много подборок (1:N). Одна подборка содержит много
новостей, одна новость входит во многие подборки (M:N между подборками и
новостями). Элементы встроены в подборку со ссылкой `articleId`; тексты статей
не копируются. Источник истины подборки — MongoDB. `userId`, непустое `name`
и массив `items` обязательны, внутри элемента — `articleId` и `addedAt`;
`note` необязателен.

```json
{
  "userId": 1,
  "name": "Почитать позже",
  "items": [
    { "articleId": 1000, "addedAt": "2026-10-02T09:00:00Z", "note": "про трансферы" }
  ]
}
```

В одной подборке не более 200 разных новостей; повторный `articleId` запрещён.
Например, список A содержит новости 1000 и 1001, список B — 1000: обе стороны
M:N могут иметь несколько связей. Лимит и отсутствие повторов должна проверять
будущая реализация; сейчас это правила модели. Ограничение числа элементов
не заменяет контроль размера документа и длины заметок.

### 4.5. Связи между сущностями

| Связь | Тип | Реализация |
|---|---|---|
| `news` (PostgreSQL) → `articles` | 1:1 для синхронизированных неудалённых новостей; временно 1:0 при отставании | `articles._id = news.id`; удалённая копия может сохраняться с `deletedAt` |
| `articles` → `article_events` | 1:N | ссылка `article_events.articleId` |
| `scrape_run` (PostgreSQL) → `import_payloads` | 1:N | ссылка `import_payloads.scrapeRunId` |
| `app_user` (PostgreSQL) → `reading_lists` | 1:N | `reading_lists.userId` |
| `reading_lists` ↔ `articles` | M:N | встроенные `items[].articleId`; новость может входить в несколько подборок |
| `app_user` (PostgreSQL) ↔ `articles` | M:N через подборки | `reading_lists.userId` и встроенные `items[].articleId` |

Между PostgreSQL и MongoDB нет внешних ключей, поэтому ссылки проверяет приложение.

## 5. Покрытие согласованных требований

| Требование | Где описано |
|---|---|
| Разделение данных и источник истины | Разделы 1 и 3: все текущие SQL-сущности, проекция и три собственные коллекции MongoDB |
| Задачи с преимуществом документной модели | T1–T4: цель чтения/записи, вложение или ссылки и ограничения выбора |
| Минимум три коллекции, связи 1:N и M:N | Четыре коллекции в разделе 4; 1:N статьи→события, M:N подборки↔статьи |

Для этого этапа проверяются проект, согласованность с SQL-схемой и корректность
JSON-примеров. Работа коллекций, права, индексы и доставка изменений требуют
отдельной реализации и проверки на MongoDB.
