# Журнал архитектурных решений · лабораторная 5

Статус решений: приняты, 2026-11-04. Основа модели — работа в PR #7;
здесь зафиксированы решения её учебной реализации и их ограничения.

## ADR-01. Владение и проекция новости

**Контекст.** SQL-аналитике, импорту, RLS и ограничениям нужны исходные
реляционные данные; карточка новости читается вместе с названиями справочников.

**Решение.** PostgreSQL остаётся источником истины для всех существующих сущностей.
MongoDB articles — производная карточка, а события, сырые ответы и подборки —
собственные документы MongoDB. Учебный CRUD статьи имитирует применение снимка.

**Альтернативы.** Перенос news в MongoDB нарушил бы текущие SQL-связи и Q1–Q8;
независимое редактирование обеих копий потребовало бы разрешения конфликтов.

**Последствия.** Нет двух равноправных владельцев новости. Будущая доставка должна
учитывать сбои после COMMIT, удаления и изменения справочников. Сейчас
синхронизация не реализована, fixtures.js содержит синтетический снимок.

## ADR-02. Ограниченное встраивание

**Контекст.** Подборка читается целиком с датами и заметками. Списки небольшие,
обновление отдельной заметки должно сохранять согласованность документа.

**Решение.** items встроены в reading_lists; максимум 200 элементов, заметка
до 1000 символов, имя до 100. В карточке также встроены снимки source/categories.
crud.js показывает `$push` и `$set` с `arrayFilters` внутри одного документа.

**Альтернативы.** Отдельная коллекция элементов потребовала бы дополнительного
чтения и согласования изменений; неограниченное встраивание создало бы риск
постоянного роста документа.

**Последствия.** Изменение одной подборки атомарно на уровне документа;
изменения справочников требуют пересборки копий. Проверка измеряет `$bsonSize`
подборки с максимальным количеством длинных заметок. MongoDB ограничивает
один BSON-документ 16 МиБ. [Встраивание](https://www.mongodb.com/docs/manual/data-modeling/embedding/),
[размер документа](https://www.mongodb.com/docs/manual/reference/limits/#bson-document-size).

## ADR-03. Ссылки для роста и повторного использования

**Контекст.** Число просмотров статьи растёт независимо от её содержимого.
Одна новость может входить во многие пользовательские подборки.

**Решение.** article_events хранит articleId; items внутри подборки также
содержит только articleId и персональные метаданные. Полный текст остаётся
в articles. Индексы поддерживают поиск событий по статье/времени и списков
по владельцу/статье. crud.js показывает `$lookup` и пересекающиеся списки A/B.

**Альтернативы.** Встраивание всех событий раздувает карточку, копирование
текстов во все подборки усложняет исправление исходной новости.

**Последствия.** Новые события вставляются независимо; при чтении карточек
подборки нужен lookup или отдельное чтение. Ссылки не становятся FK; внешние
SQL-ссылки и конкурентное удаление должно обрабатывать будущее приложение.

## ADR-04. Проверка формы и бизнес-правил на сервере

**Контекст.** Обычный JSON не гарантирует BSON long/date, а ошибки клиента
могут нарушить предел или уникальность элементов подборки.

**Решение.** schema.js задаёт `$jsonSchema`, обязательность и строгие BSON-типы,
`strict/error`. БП-1 ограничивает items до 200; БП-2 проверяет уникальность
articleId через `$map/$setUnion`; БП-3 связывает format и тип raw через `oneOf`.
Уникальный URL поддерживается отдельным индексом по инварианту PostgreSQL.

**Альтернативы.** Только клиентские проверки обходятся прямой записью.
`uniqueItems` сравнивает целые элементы и пропускает равные ID с разными заметками;
unique multikey index не запрещает повторы ключа внутри одного документа.

**Последствия.** Неверная вставка/обновление отклоняется кодом 121, конфликт URL —
11000. Вычисления над items защищены `$isArray`, чтобы неверная форма давала
отказ валидации. Наличие внешнего документа проверкой формы не обеспечивается.
[Пример MongoDB проверки массива](https://www.mongodb.com/docs/manual/tutorial/unique-indexes-schema-validation/),
[валидация выражениями](https://www.mongodb.com/docs/v8.0/core/schema-validation/specify-query-expression-rules/).

## ADR-05. Изолированный локальный стенд

**Контекст.** Для задания нужны реальные CRUD и отказы валидации, но не внешний
клиент или новый production-сервис.

**Решение.** Отдельный Compose, mongo:8.0, сеть отключена, mongod на loopback,
mongosh запускается через Docker exec. Секреты PostgreSQL не монтируются.
Сценарии принимают только явно учебные имена БД.

**Альтернативы.** Включение MongoDB в основной Compose связало бы независимые
лабораторные; опубликованный порт потребовал бы дополнительных настроек доступа.

**Последствия.** Обычный PostgreSQL-запуск не меняется. Владелец Docker доверенный;
аутентификация MongoDB и приложение не входят в этот стенд. `userId` в запросе
демонстрирует фильтрацию, но не доказывает личность клиента.

## ADR-06. Один сценарий для демонстрации и проверки

**Контекст.** Примеры в отчётах могут расходиться с фактически выполняемым кодом.

**Решение.** demo и verify исполняют одни schema/fixtures/crud. Python stdlib
управляет контейнерами и кодами выхода, не хранит копий запросов. Verify создаёт
временный проект и удаляет его в finally. Проверяются реальный отказ сервера,
сохранность документа и ненулевой exit при неожиданном успехе негативного теста.

**Альтернативы.** Только ручные примеры не подтверждают отказ неправильных
документов; дублирование CRUD в тестах могло бы проверять иной код.

**Последствия.** Журналы воспроизводимы, demo можно осматривать, ошибки нельзя
принять за успешную проверку. Artifacts остаются локальными; сдаваемые сценарии,
настройки, модель и этот журнал предназначены для сдачи в репозитории.
[Отчёт защиты](lab5-report.md) объясняет эти решения и содержит проверенные
команды и ручные примеры для каждой части лабораторной.
